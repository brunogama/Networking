# Phase 10.1 Plan 02: HTTPMacroExpansion Protocol with Shared Expansion Logic

**One-liner**: Created HTTPMacroExpansion protocol with default expansion implementation for DRY HTTP macro workflow

## Summary

Implemented the HTTPMacroExpansion protocol that encapsulates the entire 10-step HTTP macro expansion workflow using Swift's protocol extension pattern. The protocol requires only one static property (`config: HTTPMethodConfig`) from conformers, while the extension provides the complete `sharedExpansion` method that orchestrates validation, extraction, and code generation. Split helper logic into HTTPMacroExpansion+Helpers.swift to maintain file length budgets.

### Protocol Extension Wiring

The protocol extension reads the `config` static property via:
- `config.method` → Used in error messages and code generation
- `config.requiresBody` → Determines if body parameter required
- `config.allowsVoidReturn` → Determines if Void return type allowed (DELETE only)

This is the key DRY mechanism: conformers only provide configuration, extension provides all logic.

## Key Decisions

1. **Protocol extension pattern instead of inheritance**: Swift's protocol extension with default implementation provides better composition and testability
2. **Single static property requirement**: Conformers only provide `config`, making adoption trivial
3. **Split helper methods into separate file**: HTTPMacroExpansion.swift (110 lines) + HTTPMacroExpansion+Helpers.swift (245 lines) maintains file length budgets
4. **Extract private helpers for each generation step**: `generateBodyCode`, `generateHeaderCode`, `generateQueryParameterCode` keep complexity under limits
5. **Wired to InterceptorCodeGenerator**: Delegates final AST generation to existing infrastructure, no duplication
