<technical_notes>
## Swift Macro Testing Architecture

### Why @testable import fails

Swift macros are implemented as compiler plugins using SwiftCompilerPlugin. When you create a `.macro()` target:

```swift
.macro(
  name: "NetworkingMacros",
  dependencies: [
    .product(name: "SwiftCompilerPlugin", package: "swift-syntax"),
  ]
)
```

The SwiftCompilerPlugin is linked as a **plugin dependency**, not a regular library. This means:
- The macro executable can use SwiftCompilerPlugin
- Test targets importing the macro cannot access SwiftCompilerPlugin
- `@testable import NetworkingMacros` fails because SwiftCompilerPlugin symbols are missing

### Solution: Expansion-based testing

SwiftSyntaxMacrosTestSupport provides `assertMacroExpansion` which:
1. Takes macro types as a dictionary parameter (compile-time)
2. Parses input source as AST
3. Invokes macro expansion (using SwiftSyntax directly)
4. Compares output source string

This works because:
- Macro types are referenced at compile time only
- No runtime import of macro module needed
- Expansion happens in-process via SwiftSyntax

### #if canImport pattern

Using `#if canImport(NetworkingMacros)` allows:
- Tests to compile even if macro module unavailable
- Macro type references only evaluated when module available
- Graceful degradation (tests skip, don't fail)

## Gap 2: #externalMacro vs @_exported import

The plan specification (MACRO-04) incorrectly stated "@_exported import NetworkingMacros".

For Swift macros, this is WRONG because:
- Macros are compile-time constructs (not runtime types)
- @_exported import re-exports runtime symbols
- Macros must use #externalMacro to reference compiler plugin

The implementation correctly uses:
```swift
public macro API(baseURL: String) =
  #externalMacro(module: "NetworkingMacros", type: "APIMacro")
```

This is the ONLY correct way to declare a macro that's implemented in another module.
</technical_notes>
